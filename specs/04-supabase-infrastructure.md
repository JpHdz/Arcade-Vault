# SPEC 04 — Supabase infrastructure

> **Status:** Approved
> **Depends on:** SPEC 03
> **Date:** 2026-09-12
> **Objective:** Connect the app to the remote Supabase project through typed browser and server clients, a CLI-driven migrations folder and a development-only health route, without adding any table or touching the fake session.

---

## 1 — Why this spec exists

Everything the app remembers today lives in `localStorage`: the fake session in `av_user` and the saved scores in `av_scores` (`lib/session.tsx`). Competing for the highest score needs a real backend, and the project already has one provisioned: the Supabase project `mgzomtuaeejnwfsfugto` (`https://mgzomtuaeejnwfsfugto.supabase.co`), wired into `.mcp.json`.

At the time of writing that project is empty: no tables in `public`, no migrations applied. The repo has no `@supabase/*` package, no CLI and no `supabase/` folder.

"Implementing Supabase" in one go would mix four domains — plumbing, authentication, schema and data migration. This spec does the plumbing only, so that the future auth spec and the future scores spec each start from a known-good connection and only take their own decisions.

---

## 2 — Scope

**In:**

- Runtime dependencies `@supabase/supabase-js` and `@supabase/ssr`; the Supabase CLI as the devDependency `supabase`.
- `supabase init` output committed: `supabase/config.toml`, `supabase/.gitignore`, and an empty `supabase/migrations/` kept by a `.gitkeep`.
- The repo linked to the remote project `mgzomtuaeejnwfsfugto` (a one-time manual step; the link state is git-ignored).
- Three npm scripts: `db:new`, `db:push`, `db:types`.
- `lib/supabase/config.ts` — reads the two public variables and reports whether Supabase is configured.
- `lib/supabase/client.ts` — browser client factory built with `@supabase/ssr`.
- `lib/supabase/server.ts` — server client factory built with `@supabase/ssr` over Next's async `cookies()`.
- `lib/supabase/database.types.ts` — generated by the CLI and committed.
- `app/api/health/supabase/route.ts` — a development-only `GET` that exercises the real server client; `404` in production.
- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` added to `specs/.env.example`, and the existing `SUPABASE_DB_PASSWORD` entry re-documented as CLI-only.
- Degraded mode: with the variables missing, `npm run build` passes, nothing throws at import, and both factories return `null`.

**Out of scope (for future specs):**

- Supabase Auth, replacing `lib/session.tsx`, or any change to `/sign-in`. The fake session keeps working exactly as today.
- A `proxy.ts` that refreshes the Supabase session on every request. It arrives with the auth spec, when there is a session to refresh.
- Any table, view, function, RLS policy, trigger or storage bucket. The remote `public` schema stays empty.
- Moving `av_scores` to the database, or reading the Hall of Fame from it.
- The secret key (`sb_secret_…`) and any admin client that bypasses RLS.
- The legacy JWT `anon` key.
- A local Docker stack (`supabase start`) and Supabase branching.
- CI jobs that push migrations or check that the generated types are fresh.
- Realtime, Edge Functions, Storage.
- Moving `specs/.env.example` to the project root.

## 3 — Data model

This feature introduces **no database schema**. The remote `public` schema stays empty. What it does introduce is the code-level contract every later Supabase spec will build on.

### Environment variables

| Variable                               | Reaches the browser | Read by                  | Purpose                                                |
| -------------------------------------- | ------------------- | ------------------------ | ------------------------------------------------------ |
| `NEXT_PUBLIC_SUPABASE_URL`             | yes                 | `lib/supabase/config.ts` | Project API URL, `https://<ref>.supabase.co`.          |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | yes                 | `lib/supabase/config.ts` | Publishable key, `sb_publishable_…`. Public by design. |
| `SUPABASE_DB_PASSWORD`                 | **no**              | the Supabase CLI only    | Database password for `supabase link` and `db push`.   |

`SUPABASE_DB_PASSWORD` is never read by application code and never gains a `NEXT_PUBLIC_` prefix.

### `lib/supabase/config.ts`

```ts
export interface SupabaseConfig {
  url: string;
  publishableKey: string;
}

/** `null` when either variable is missing or blank. */
export function getSupabaseConfig(): SupabaseConfig | null;

export function isSupabaseConfigured(): boolean;
```

Both variables are read with literal property access (`process.env.NEXT_PUBLIC_SUPABASE_URL`), never through a dynamic key, so Next can inline them into the browser bundle.

### Client factories

```ts
// lib/supabase/client.ts
export function createSupabaseBrowserClient(): SupabaseClient<Database> | null;

// lib/supabase/server.ts
export async function createSupabaseServerClient(): Promise<SupabaseClient<Database> | null>;
```

- Both return `null` when `getSupabaseConfig()` is `null`. Neither throws for missing configuration.
- Neither builds a client at module scope. Each call builds one; nothing is cached across requests on the server.
- `server.ts` must never be imported from a `"use client"` module.

### `lib/supabase/database.types.ts`

Generated by `npm run db:types`, committed, never edited by hand. It exports `Database`. With an empty `public` schema its `Tables` map is empty; that is expected.

### Health route response

```ts
type SupabaseHealth =
  | { configured: false; reachable: false }
  | { configured: true; reachable: true; latencyMs: number }
  | { configured: true; reachable: false; error: string };
```

| Situation                               | HTTP status | Body                                               |
| --------------------------------------- | ----------- | -------------------------------------------------- |
| `NODE_ENV === "production"`             | `404`       | empty                                              |
| Variables missing                       | `503`       | `{ configured: false, reachable: false }`          |
| Round trip succeeded                    | `200`       | `{ configured: true, reachable: true, latencyMs }` |
| Round trip failed (bad key, network, …) | `503`       | `{ configured: true, reachable: false, error }`    |

Every response carries `Cache-Control: no-store`. `error` is the SDK's message; the body never contains the key, the URL's credentials, or the database password.

### npm scripts

| Script     | Command                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------- |
| `db:new`   | `supabase migration new`                                                                  |
| `db:push`  | `supabase db push`                                                                        |
| `db:types` | `supabase gen types typescript --linked --schema public > lib/supabase/database.types.ts` |

### Repository layout added

```
supabase/
  .gitignore          # generated by `supabase init` (ignores .temp/, .branches/, .env)
  config.toml         # generated by `supabase init`
  migrations/
    .gitkeep
lib/supabase/
  config.ts
  client.ts
  server.ts
  database.types.ts
app/api/health/supabase/
  route.ts
```

## 4 — Implementation plan

Each step leaves the project building.

1. **Read the guides first.** As `CLAUDE.md` requires, before writing any Next.js code read `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md`, `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`, `node_modules/next/dist/docs/01-app/02-guides/environment-variables.md` and `node_modules/next/dist/docs/01-app/02-guides/data-security.md`. Then read Supabase's current server-side-rendering guide for Next.js through the Supabase MCP `search_docs` tool, for the `createBrowserClient` / `createServerClient` cookie API. Do not write the factories from memory.
2. **Dependencies.** `npm install @supabase/supabase-js @supabase/ssr` and `npm install -D supabase`. Confirm the installed versions (latest at the time of writing: `2.116.0`, `0.12.7` and `2.117.0`) and use their own API surface. Confirm `npx supabase --version` runs.
3. **Environment.** Add `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to `specs/.env.example`, each with a comment and a placeholder (`https://your-project-ref.supabase.co`, `sb_publishable_...`). Rewrite the comment on `SUPABASE_DB_PASSWORD` to say it is read only by the CLI, never by the app. `.gitignore` already whitelists `.env.example`, so no force-add is needed. Put the real values in `.env.local`: the URL from the MCP `get_project_url` tool, the key from `get_publishable_keys` or the dashboard.
4. **CLI init.** Run `npx supabase init` at the project root. Decline any editor-settings prompt; it must not create `.vscode/`. Add `supabase/migrations/.gitkeep`. Check that the generated `supabase/.gitignore` ignores `.temp/` and `.branches/`.
5. **Link.** The user runs `! npx supabase login` once (it is interactive). Then `npx supabase link --project-ref mgzomtuaeejnwfsfugto`, providing the database password from `SUPABASE_DB_PASSWORD`. Verify with `npx supabase migration list`: it must connect and list zero local and zero remote migrations.
6. **Scripts.** Add `db:new`, `db:push` and `db:types` to `package.json` exactly as the table above says.
7. **Types.** Run `npm run db:types` and commit `lib/supabase/database.types.ts`. Confirm it exports `Database`.
8. **Config.** Create `lib/supabase/config.ts` with `getSupabaseConfig()` and `isSupabaseConfigured()`.
9. **Browser client.** Create `lib/supabase/client.ts` with `createSupabaseBrowserClient()`, typed with `Database`, returning `null` when unconfigured. Nothing imports it yet.
10. **Server client.** Create `lib/supabase/server.ts` with `createSupabaseServerClient()`: `await cookies()`, pass `getAll` / `setAll` to `createServerClient`, and wrap `setAll` in a `try/catch`. Server Components cannot write cookies, and until the auth spec adds `proxy.ts` there is no session to refresh. A one-line comment says so. Return `null` when unconfigured.
11. **Health route.** Create `app/api/health/supabase/route.ts` exporting `GET`, following the status table in the data model. In production return `404` before touching anything. When unconfigured return the `configured: false` body. Otherwise build the server client and make **one** real network round trip that the API rejects when the key is invalid. `supabase.storage.listBuckets()` is the candidate; confirm against the installed SDK that a wrong key actually yields an error, and pick another call if it does not. Measure `latencyMs` around that call only.
12. **Verification.** Run `npm run lint` and `npm run build`, with `.env.local` present and with it temporarily renamed. Then exercise the route with `npm run dev` and with `npm run build && npm run start` as the acceptance criteria describe.

- [ ] `npm run build` completes with no errors and `npm run lint` reports no errors.

- [ ] `package.json` lists `@supabase/supabase-js` and `@supabase/ssr` under `dependencies`, `supabase` under `devDependencies`, and the scripts `db:new`, `db:push` and `db:types`.
- [ ] `supabase/config.toml`, `supabase/.gitignore` and `supabase/migrations/.gitkeep` are tracked; nothing under `supabase/.temp/` is (`git ls-files supabase`).
- [ ] `npx supabase migration list` connects to the linked project and reports zero local and zero remote migrations, with no error.
- [ ] Running `npm run db:types` again leaves `lib/supabase/database.types.ts` with no diff.
- [ ] `lib/supabase/database.types.ts` exports `Database`, and both factories are typed as returning `SupabaseClient<Database> | null`.
- [ ] In `npm run dev` with valid variables, `GET /api/health/supabase` answers `200` with `{ "configured": true, "reachable": true, "latencyMs": <number> }`.

- [ ] With both Supabase variables removed, the same request answers `503` with `{ "configured": false, "reachable": false }`, and the server log shows no exception.
- [ ] After `npm run build && npm run start`, `GET /api/health/supabase` answers `404`.
- [ ] Every health response carries `Cache-Control: no-store`.
- [ ] No health response body contains the publishable key or the database password.
- [ ] `SUPABASE_DB_PASSWORD` appears in no file under `app/`, `components/` or `lib/`.
- [ ] No module marked `"use client"` imports `lib/supabase/server.ts`.
- [ ] `specs/.env.example` lists `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_DB_PASSWORD` with placeholders only; `.env.local` is not tracked, and no real key or password appears anywhere in the tree.
- [ ] Neither `proxy.ts` nor `middleware.ts` exists at the project root.
- [ ] `lib/session.tsx` has no diff, and `/home`, `/games`, `/about` and `/sign-in` render as before with no new errors in the browser console.
- [ ] The remote `public` schema still has zero tables (MCP `list_tables`).

## 6 — Decisions taken and discarded

| Decision              | Taken                                                                           | Discarded                                                 | Why                                                                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scope                 | Infrastructure only                                                             | Infra + auth; infra + scores table; everything at once    | Everything at once spans four domains and does not fit one sentence. Scores without auth would need anonymous writes or an open RLS policy. Auth and scores each get their own spec on top of this one.   |
| Development database  | The remote cloud project `mgzomtuaeejnwfsfugto`                                 | Local Docker stack; local + remote                        | No Docker on a Windows machine to maintain, and the remote project is empty, so there is no data to break. The cost is recorded under risks.                                                              |
| Schema management     | Versioned SQL in `supabase/migrations/`, applied with `supabase db push`        | MCP `apply_migration` only; changes in the dashboard      | The schema lives in git and goes through review like any other code. MCP-only or dashboard changes leave no trace in the repo.                                                                            |
| CLI installation      | devDependency `supabase` plus npm scripts                                       | Global install; no CLI, MCP only                          | The version is pinned in `package-lock.json` and every clone gets the same one. MCP-only contradicts versioned migrations pushed with the CLI.                                                            |
| Keys                  | Publishable key only                                                            | Publishable + secret key; legacy JWT `anon` key           | Nothing needs to bypass RLS yet, and a secret key that is not used is a secret key that can only leak. The legacy `anon` key is being retired in favour of publishable keys.                              |
| Missing configuration | Degrade: factories return `null`, `isSupabaseConfigured()` guard, build passes  | Fail fast at import or at startup                         | Same stance as Resend in SPEC 03: anyone can clone and build without credentials, and CI builds without secrets.                                                                                          |
| Factory contract      | Return `SupabaseClient<Database> \| null`                                       | Throw when unconfigured                                   | The type system forces every future caller to handle the degraded branch, instead of relying on each one to remember a guard.                                                                             |
| Factory names         | `createSupabaseBrowserClient` / `createSupabaseServerClient`                    | `createClient` in both files, as in Supabase's guide      | Two functions with the same name in two modules invite importing the wrong one; the server one must never reach the browser.                                                                              |
| Session refresh proxy | Deferred to the auth spec                                                       | A `proxy.ts` now                                          | With no auth there is no session to refresh; it would run on every request for nothing.                                                                                                                   |
| Connection check      | Development-only `GET /api/health/supabase` through the real server client      | A standalone node script; relying on a baseline migration | It exercises `lib/supabase/server.ts` itself, with Next's env loading and cookies. A script would test the network but not the app's clients; a migration would test the database but not the app's keys. |
| Health status codes   | `200` only when reachable, `503` otherwise, `404` in production                 | Always `200` with a body flag                             | A status code is what `curl -f` and any future uptime check read without parsing JSON.                                                                                                                    |
| Initial migration     | None; `supabase/migrations/` starts empty with a `.gitkeep`                     | An empty baseline migration                               | A no-op migration would sit in the history forever. The link is verified with `migration list` instead.                                                                                                   |
| Generated types       | Committed `lib/supabase/database.types.ts`, regenerated with `npm run db:types` | Generated during `npm run build`                          | Generating at build time would make every build need the CLI and an access token, breaking the "builds without credentials" rule.                                                                         |
| `.env.example` place  | Stays at `specs/.env.example`                                                   | Moving it to the project root                             | That is where it lives today and its header already explains copying it to the root as `.env.local`. Moving it is unrelated to Supabase.                                                                  |

## 7 — Identified risks

- **The publishable key is public by design.** It ships in the browser bundle, so security rests entirely on Row Level Security. The moment a future spec creates a table without RLS enabled, anyone with the key can read and write it. Every schema spec after this one must enable RLS on each table it creates.
- **Migrations go straight to the only database.** With no local stack and no branching, `npm run db:push` applies SQL directly to the project the app uses. The mitigation is reviewing each migration before pushing it; a local stack or branching can land in its own spec if this starts to hurt.
- **`NEXT_PUBLIC_` values are inlined at build time.** A dynamic lookup such as `process.env[name]` yields `undefined` in the browser. Changing the URL or key also requires a rebuild, not only a restart.
- **The CLI does not read `.env.local`.** `supabase link` and `db push` need the database password from the shell or from the prompt, not from Next's env files. `supabase login` is interactive and must be run by the user (`! npx supabase login`); an agent cannot complete it.
- **The `supabase` npm package downloads a native binary on install.** Antivirus or network restrictions on Windows can make `npm install` fail at that step. The fallback is a global install, recorded here instead of silently switching.
- **Stale generated types.** A change made in the dashboard, or a migration pushed without running `npm run db:types`, leaves `database.types.ts` lying about the schema. The convention is that every migration is followed by regenerating the types in the same commit.
- **The health route leaking into production.** It reveals whether the backend is reachable and echoes SDK errors. The `NODE_ENV` check has its own acceptance criterion against `npm run start`.
- **Cookie writes are swallowed on the server.** The `try/catch` around `setAll` is harmless while there is no auth. Once auth lands, refreshed tokens will silently fail to persist unless that spec adds `proxy.ts`.
